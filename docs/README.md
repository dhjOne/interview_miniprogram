# 小程序文档中心（docs）

本目录统一管理 `interview_miniprogram` 的**项目标准**与**技术方案**。  
后续凡涉及架构、功能落地、跨端约定、联调说明的文档，一律放在此处，不再散落在聊天记录或临时文件中。

## 目录结构

```text
docs/
├── README.md                 # 本文件：索引 + 管理规范（入口）
├── standard/                 # 长期有效的开发标准 / AI 知识库
│   ├── README.md
│   ├── PROJECT_STANDARD.md
│   ├── AI_KNOWLEDGE_BASE.md
│   └── CROSS_REPOSITORY_STANDARD.md
├── tech/                     # 功能级技术方案（设计 + 落地结果）
│   ├── README.md
│   └── *.md
└── *.md                      # 历史方案可暂留根目录，新文档勿再直接堆在根下
```

| 目录        | 放什么                                                  | 不放什么                 |
| ----------- | ------------------------------------------------------- | ------------------------ |
| `standard/` | 编码规范、目录约定、跨仓协作、给 AI 的稳定上下文        | 某个功能的一次性方案     |
| `tech/`     | 功能/模块技术方案、接口约定、前后端联调说明、已落地结论 | 纯会议纪要、无结论的草稿 |

## 命名规范

技术方案文件放在 `docs/tech/`，命名：

```text
YYYY-MM-<topic-kebab-case>.md
```

示例：

- `2026-07-question-share.md` — 题目分享（转发 / URL Link / 免登可读）
- `2026-07-mobile-admin.md` — 移动管理台（若从根目录迁入可沿用此风格）

可选在文首加状态标记：`草稿` / `已评审` / `已落地` / `已废弃`。

## 技术方案模板（tech）

每份 `docs/tech/*.md` 建议包含：

1. **元信息**：时间、状态、涉及端（小程序 / 后端 / 管理台）
2. **目标与范围**
3. **方案结论**（最终选了什么，为什么）
4. **前后端约定**（接口、字段、鉴权）
5. **关键实现落点**（主要文件路径）
6. **行为与边界**（登录、异常、配额等）
7. **验证清单**
8. **后续可选优化**（未做的明确写出，避免遗忘）

## 写入与维护流程

1. **开做功能前**：在 `docs/tech/` 建方案文档（可先标「草稿」），再改代码。
2. **落地后**：把状态改为「已落地」，补齐接口与文件落点；与实现不一致时以代码为准并回写文档。
3. **重大变更**：在原文追加「修订记录」，或新建版本文件并在 `tech/README.md` 索引里指向最新版。
4. **废弃**：文首标「已废弃」并写明替代文档，不要直接删历史结论。
5. **索引**：每新增一份 tech 文档，必须更新 `docs/tech/README.md` 与本文件「文档索引」。

## AI / 协作约定

- 讨论或落地**新功能技术方案**时：文档写入 `docs/tech/`，并更新索引。
- 改**通用规范**时：更新 `docs/standard/`，而不是写进某个功能方案。
- 引用时优先用仓库相对路径，例如 `docs/tech/2026-07-question-share.md`。
- **下班 / 换设备前**：把未完成项写入对应 tech 文档的 backlog，并 **commit + push**；下一台机器以文档为准，不依赖本机聊天记录。
